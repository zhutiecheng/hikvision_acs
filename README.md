# 海康威视门禁 · Home Assistant 集成

把海康威视门禁一体机（DS-K1T 系列等）接进 Home Assistant：

- **远程开门** — 一个按钮实体、一个服务，可直接进自动化
- **上报谁用什么方式开门** — 门禁事件实体，自动化里直接选，不用解析报文
- **门铃自动推到中控屏** — 附带的蓝图 + 条件卡片，不需要装任何前端插件
- **门口画面摄像头** — 走 HA 自带的 stream 组件

已在 **DS-K1T341BM（固件 V3.7.80）** 上端到端实测通过，累计采到 50+ 条真实事件、
7 张联动抓拍图。事件码语义全部来自真机实测，不是抄文档。

> ⚠️ **不要用 485 做二次开发。** 该系列机器的 RS-485 是海康私有的设备间总线
> （接门控安全模块，或把一体机当读卡器用），没有开放协议，也拿不到身份和开门方式。
> 本集成全部走网络（ISAPI）。

---

## 安装

### 方式一：HACS（推荐给客户）

1. HACS → 集成 → 右上角菜单 → **自定义存储库**
2. 填入本仓库地址，类别选 **Integration**
3. 搜索「海康威视门禁」并安装
4. **重启 Home Assistant**

### 方式二：手动

把 `custom_components/hikvision_acs/` 整个目录复制到 HA 配置目录下的
`custom_components/` 里，然后重启 HA。

之后：**设置 → 设备与服务 → 添加集成 → 搜「海康威视门禁」**，填设备 IP、账号、密码。
不需要编辑任何 YAML。

### 前置条件

- 门禁设备与 HA **在同一局域网**（设备要能访问到 HA，才能推送实时事件）
- 设备已激活，知道 admin 密码
- HA 用 HTTP 访问（若配了 HTTPS 自签证书，设备可能拒绝推送，见「排查」）

## 你会得到什么

| 实体 | 类型 | 用途 |
|---|---|---|
| **门禁事件** | `event` | **自动化触发入口**：门铃 / 认证通过 / 认证失败 / 门锁打开 / 门锁关闭 / 开门按钮 / 远程开门 |
| 开门 | `button` | 按一下就开门 |
| 门锁 | `binary_sensor` | 门锁继电器状态（不是门扇开合，见下） |
| 在线 | `binary_sensor` | 设备可达性 |
| 最后开门人 | `sensor` | 最近一位通过认证的人 |
| 最后开门方式 | `sensor` | 人脸 / 刷卡 / 开门按钮 / 远程开门 |
| 最后事件 | `sensor` | 原始事件（含未确认语义的码，便于现场排查） |
| 今日开门次数 | `sensor` | 按门锁打开事件计数 |
| 门口画面 | `camera` | RTSP 流 + 抓拍图 |

服务 `hikvision_acs.open_door`（可选 `entry_id`、`door`）可在自动化/脚本里调用。

## 门铃自动推到中控屏

集成附了蓝图 `blueprints/automation/hikvision_acs/doorbell_popup.yaml`。

1. 创建一个辅助元素：**设置 → 设备与服务 → 辅助元素 → 开关**，命名「访客呼叫」
2. **设置 → 自动化与场景 → 蓝图 → 导入蓝图**（选附带的那个文件）
3. 用蓝图建自动化：门禁事件实体 + 显示开关 + 门口摄像头 + 停留秒数
4. 仪表盘上放一张**条件卡片**：条件为「访客呼叫 = 开」，卡片选「门口画面」

效果：有人按门铃 → 开关打开 → 中控屏自动出现门口画面 → 30 秒后自动消失。

之所以用「开关 + 延时」而不是直接弹窗：不需要额外装前端插件，平板、大屏、手机
任何仪表盘都能用。

**想要更低延迟**：HA 自带 stream 走 HLS，延迟 3~10 秒，门铃场景偏慢。建议另外装
go2rtc/WebRTC 相关加载项，让摄像头的流走 WebRTC（实测抓单帧约 0.7 秒）。

## 事件是怎么进来的（排查时会用到）

集成用**两条互补的通道**：

**主通道 — HTTP 监听（设备主动推）。** 启动时自动把设备的
`/ISAPI/Event/notification/httpHosts` 指向 HA 的 webhook
`http(s)://<你的HA>/api/webhook/<id>`。设备每个事件 POST 一次，包含二进制抓拍图。

**兜底 — 轮询。** 按配置的间隔查 `/ISAPI/AccessControl/AcsEvent`，用设备侧全局递增的
`serialNo` 去重补齐。网络抖动或 HA 重启期间漏掉的事件靠它补回来。

日志里出现 `已让设备把事件推送到 ...` 就代表推送配置成功。

### 为什么不用 alertStream 长连接

实测教训，值得写下来：该设备**只允许一条 alertStream 会话**，而且因为它是「有事件才写
数据」，客户端异常断开后设备**长时间察觉不到对端已死**，那条会话一直被占，之后所有新
连接被拒——有时返回 404，有时干脆不响应（TCP 连上了但不下发响应头）。此时快速重试只会
把设备占得更死。做在 HA 里这种故障极难排查，所以主通道用短连接。

## 排查

**收不到实时事件（只有轮询延迟）**
1. 看 HA 日志有没有 `已让设备把事件推送到`
2. 确认设备能访问 HA：在同网段另一台机器上
   `curl -X POST http://<HA>:8123/api/webhook/<id> -d '{}'`
3. **HA 用了 HTTPS 自签证书**：设备多半会拒绝推送。给 HA 配正式证书，或让 HA 同时监听 HTTP
4. 改了 HA 地址后，重载集成即可重新下发配置

**添加集成时报「认证失败」**
用户名默认 `admin`；密码是设备**激活时**设置的，不是出厂密码。

**门锁状态看起来不对**
「门锁」反映的是**门锁继电器**（开锁/上锁），不是门扇实际开合。要拿门扇状态得把
门磁接到设备的 `SENSOR` 端子，设备才会产生门磁类事件。

**远程开门失败**
服务会返回带 `error` 的结果。常见原因是门号不对，或门处于常闭/反潜回等门禁计划限制下。

## 给集成开发者的说明

```bash
python3 tools/validate_integration.py     # 离线校验，155 项，可当 CI 门禁
python3 tools/acs_probe.py --help         # 现场调试：探测设备、采样真实事件
```

HA 跑在另一台主机上时，开发机装不了 HA Core，所以校验分三层：纯逻辑单测
（`eventcodes.py` 不依赖 HA，事件码映射和 `currentVerifyMode` 陷阱全部实测覆盖）、
结构校验（manifest / 翻译 / 平台齐备性）、静态分析（未定义名字）。

**改动事件码表后务必跑一遍**——它会检查每个登记的码是否真在设备自述的可上报范围内。
这条校验已经抓到过一次真实错误：我凭公开文档把「远程关门」登记成 `(5, 1025)`，
而设备声明里 `0x401` 只属于「操作」大类，应为 `(3, 1025)`。

`docs/DS-K1T341BM-接入方案.md` 有完整的真机实测记录，包括设备自述的事件码清单、
`currentVerifyMode` 为什么不能用来判断开门方式、以及上面那个 alertStream 的坑。
